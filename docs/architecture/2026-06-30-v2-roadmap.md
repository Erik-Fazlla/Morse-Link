# V2 Implementation Roadmap

**Status:** Approved pending one final review. **Living document.** No implementation until final review.
**Date:** 2026-06-30
**Companions:** `2026-06-30-v2-optical-comms-architecture.md`, `2026-06-30-physical-layer-study.md`, `2026-06-30-vision-engine-design.md`

## Permanent constraints (apply to every milestone)
- Two completely unmodified smartphones. Zero hardware budget. Offline only.
- V1 (Morse) remains fully functional throughout V2 development (frozen; critical bug fixes only).
- V2 is **additive & modular** (new `lib/v2/` namespace; V1 `lib/features/` untouched).
- **Every milestone leaves the project in a runnable state** (builds, `flutter test` green, `flutter analyze` 0 new; incomplete work behind a flag).

## Risk-first principle
The architecture rests on unproven **device-level assumptions**. Phase 1 is **instrumented measurement spikes**, not features — they produce data that confirms or revises the living docs *before* any large subsystem is built. Highest-risk assumptions: ① frame-timestamp precision, ② sustained frame rate under load, ③ gyro↔camera time-sync usability, ④ SNR-domain weak-source range gain, ⑤ mains-flicker vs modulation separability.

## Phase 0 — Foundations (no camera, no subsystems)

### M00 — Define measurable success metrics *(preliminary — precedes E1)*
- **Goal:** establish the concrete, measurable yardsticks every experiment and subsystem is judged against, so E1–E4 have explicit pass/fail targets. Deliverable is a metrics table appended to the living docs.
- **Why this order:** experiments are meaningless without predefined success thresholds; this prevents "looks fine" subjectivity and lets each experiment cleanly pass or fail.
- **Metrics to define (initial targets — refine at review):**
  - **Range (night, reliable):** decode distance at which framed-message success ≥95%. Baseline V1 ≈ 8–10 m; V2 must ≥ match, then extend.
  - **Message reliability:** ≥95% framed-message delivery at target range (with FEC); CRC-detected undetected-error rate ≈ 0.
  - **Idle false-positive rate:** ≈ 0 spurious decodes per minute while idle or panning (carry V1's hard-won standard).
  - **Timing jitter budget:** frame-timestamp jitter < ~20% of the chosen symbol period (exact bound set by E1).
  - **Frame rate:** minimum sustained fps for the target symbol rate (bound set by E1).
  - **Motion tolerance:** decode holds under a defined hand-motion profile (e.g. ≤ ~30°/s pan) — exact profile from E2.
  - **End-to-end latency:** acceptable message latency bound (define, e.g. ≤ a few seconds for a short message).
  - **Device coverage:** works on ≥ 3 devices spanning low/mid/high tier Android.
  - **Thermal/CPU:** sustained receive for ≥ 5 min without thermal throttling or frame-rate collapse.
- **Files/modules:** none (documentation only — update the living docs with a Metrics section).
- **Dependencies:** none.
- **Validation:** metrics are specific, measurable, and each maps to at least one experiment or milestone.
- **Success criteria:** approved metrics table; every E1–E4 references its target(s) from it.
- **Rollback:** N/A (documentation).
- **Difficulty:** S. **Impact:** **Critical** (defines "done" for everything downstream).

### M0 — V2 module skeleton + interfaces + entry flag
- **Goal:** create `lib/v2/` with empty interface contracts (`FrameSource`, `VisionEngine`, `SignalExtractor`, `Synchronizer`, `Demodulator`, `Modulator`, `FecCodec`, `FrameCodec`, `Emitter`) and a hidden "V2 Lab" entry from home (debug only).
- **Why this order:** establishes the additive boundary and the home for experiments, without touching V1.
- **Files/modules:** new `lib/v2/contracts/*`, `lib/v2/lab/`; one additive `kDebugMode` button in home screen.
- **Dependencies:** M00.
- **Validation:** app builds; V1 fully works; V2 Lab opens; `flutter test` green.
- **Success criteria:** interfaces compile; V1 regression untouched; analyze 0 new.
- **Rollback:** delete `lib/v2/` + the debug button; V1 unaffected.
- **Difficulty:** S. **Impact:** Med (enables everything).

## Phase 1 — Risk-reduction experiments (measure before building)

> **Review policy (per approval): STOP for an architecture review after EACH experiment (E1, E2, E3, E4).** Do not start the next experiment or any subsystem until the review of the just-completed experiment is done and the living docs are updated. Each review decides: assumption confirmed / design revised / approach changed.

### E1 — Frame timing & frame-rate characterization
- **Status: IN PROGRESS.** Phone A measured (23.16 fps, jitter σ 19.6 ms, p90 61 ms, max 194 ms) — see `2026-06-30-v2-success-metrics.md` §E1 Findings for full analysis. **Phone B (≥2 devices) still required before this closes and E2 begins**, per the Validation criterion below. Interim conclusions: no Vision Engine structural change; wall-clock timestamps accepted; U-STD revised 120 ms → ~300 ms (interim).
- **Goal:** log per-frame timestamps (`DateTime.now()` and any platform/sensor timestamp), inter-frame intervals, sustained fps, and per-frame processing latency under realistic load.
- **Why this order:** all V2 timing/clock-recovery depends on this; if jitter/fps are bad the PHY-timing design must change before it's built.
- **Files/modules:** `lib/v2/lab/timing_probe.*` (diagnostic only).
- **Dependencies:** M0, M00.
- **Validation:** run on ≥2 real Android devices; export interval/jitter/fps/latency histograms.
- **Success criteria (vs M00):** jitter within the timing budget; sustained fps ≥ the target-symbol-rate minimum; numbers recorded in living docs.
- **Rollback:** remove probe (data already captured).
- **Difficulty:** M. **Impact:** **Critical**.
- **▶ STOP — Architecture review E1:** confirm timing budget & symbol-rate ceiling; update PHY-timing assumptions. Proceed only after sign-off.

### E2 — Gyro ↔ camera time-sync probe
- **Goal:** log gyroscope alongside frames; measure offset/rate and whether IMU-predicted shift correlates with observed image motion.
- **Why this order:** the motion-robustness strategy hinges on IMU usability; confirm before designing the tracker's motion-comp.
- **Files/modules:** `lib/v2/lab/imu_probe.*`.
- **Dependencies:** M0, E1 (+ its review).
- **Validation:** wave the phone; compare predicted vs actual spot displacement; per-device.
- **Success criteria (vs M00):** IMU usable for motion prediction (quantified) meeting the motion-tolerance target, OR documented vision-only fallback.
- **Rollback:** remove probe.
- **Difficulty:** M. **Impact:** High.
- **▶ STOP — Architecture review E2:** decide IMU-fusion vs vision-only motion-comp; update Vision-Engine doc. Proceed only after sign-off.

### E3 — SNR-domain weak-source detection spike (range assumption)
- **Goal:** minimal adaptive background + σ + peak ≥ k·σ on a real flashlight at increasing night distances; record max detection range and SNR-vs-distance. No tracking/decode.
- **Why this order:** validates the core Vision-Engine range claim cheaply before building all nine modules.
- **Files/modules:** `lib/v2/lab/snr_detect_probe.*`.
- **Dependencies:** M0, E1 (+ its review).
- **Validation:** night field test at measured distances; compare against V1 ≈ 8–10 m.
- **Success criteria (vs M00):** SNR-domain detection ≥ V1 range; range-vs-SNR curve recorded; confirms/revises matched-filter & integration plan.
- **Rollback:** remove probe.
- **Difficulty:** M. **Impact:** **Critical**.
- **▶ STOP — Architecture review E3:** confirm the range thesis; adjust detection/integration plan. Proceed only after sign-off.

### E4 — Mains-flicker vs modulation separability spike
- **Goal:** record temporal signatures of common ambient lights (50/60 Hz LED/fluorescent, incandescent, daylight) vs a modulated torch at the device frame rate; check aliasing that could fool coherence arbitration.
- **Why this order:** the "select the coherently-modulating source" assumption must hold or false-locks return.
- **Files/modules:** `lib/v2/lab/flicker_probe.*`.
- **Dependencies:** M0, E1 (+ its review).
- **Validation:** point at various lights + a real transmitter; inspect variance/coherence maps.
- **Success criteria (vs M00):** a robust separability metric exists (or the modulation band avoids mains aliasing), consistent with the idle false-positive target.
- **Rollback:** remove probe.
- **Difficulty:** M. **Impact:** High.
- **▶ STOP — Architecture review E4:** confirm arbitration approach & modulation band; update docs. Proceed to Phase 2 only after sign-off.

## Phase 2 — Vision Engine MVP (behind the fixed `Track` contract)

### MV1 — Acquisition + Background/σ (SNR frame)
- **Goal:** modules 1–2: camera abstraction (Y-plane, best timestamp per E1), adaptive local background + σ, output an SNR frame.
- **Why this order:** SNR domain is the substrate every later module needs; informed by E1/E3.
- **Files/modules:** `lib/v2/vision/acquisition.*`, `background_model.*`.
- **Dependencies:** E1, E3 (+ reviews).
- **Validation:** unit tests on synthetic frames (known blob/background → expected σ/SNR); device sanity in Lab.
- **Success criteria:** device-invariant SNR output; tests green; runnable Lab view.
- **Rollback:** revert milestone; Lab probes still work.
- **Difficulty:** M. **Impact:** High.

### MV2 — Candidate detection (peak ≥ k·σ + variance map)
- **Goal:** module 3: emit candidates with peakSNR + modulation score.
- **Why this order:** needs MV1's SNR frame; feeds tracking.
- **Files/modules:** `lib/v2/vision/candidate_detector.*`.
- **Dependencies:** MV1, E4.
- **Validation:** synthetic-frame unit tests (blob present/absent, noise-only → none); idle-rejection test.
- **Success criteria:** detects weak blob, rejects noise; ≈0 false candidates idle.
- **Rollback:** revert; MV1 stands.
- **Difficulty:** M. **Impact:** High.

### MV3 — Kalman tracker + ROI prediction (+ IMU shift)
- **Goal:** module 5 (+4): Kalman predict/update, Mahalanobis gating, track lifecycle; ROI prediction via IMU shift (per E2) to ride motion/OFF gaps.
- **Why this order:** the motion-robustness payoff; depends on candidates (MV2) and E2.
- **Files/modules:** `lib/v2/vision/tracker.*`, `motion_comp.*` (reuse a proven Kalman impl).
- **Dependencies:** MV2, E2.
- **Validation:** synthetic moving-blob + dropout tests; device motion test vs V1.
- **Success criteria:** stable track through motion/dropouts where V1 broke; meets motion-tolerance metric.
- **Rollback:** revert to MV2.
- **Difficulty:** L. **Impact:** **Critical**.

### MV4 — Sub-pixel centroid + arbitration + `Track` output
- **Goal:** modules 6,7,9: PSF/weighted centroid, coherence arbitration, emit protocol-agnostic `Track` stream + telemetry.
- **Why this order:** completes the Vision Engine to its fixed contract; unblocks all PHY work.
- **Files/modules:** `lib/v2/vision/localizer.*`, `arbiter.*`, `vision_engine.*`.
- **Dependencies:** MV3, E4.
- **Validation:** synthetic end-to-end (frames → correct `Track`); device: clean intensity-vs-time on a real transmitter.
- **Success criteria:** stable `Track` stream ≥ V1 extraction quality; contract frozen.
- **Rollback:** revert; MV3 track still usable.
- **Difficulty:** M. **Impact:** **Critical**.

## Phase 3 — PHY end-to-end (prove the stack)

### MP0 — Wrap V1 Morse as Profile 0 (behind V2 interfaces)
- **Goal:** reuse V1 translate/timing/decode as a V2 `Modulator`/`Demodulator` consuming the `Track` stream; decode Morse through the V2 pipeline.
- **Why this order:** proves the abstractions with known-good decode before a new PHY; immediate working V2 path.
- **Files/modules:** `lib/v2/phy/profile0_morse/*` (adapters; V1 code unchanged).
- **Dependencies:** MV4.
- **Validation:** V2 pipeline decodes a real Morse transmission; compare to V1 standalone.
- **Success criteria:** parity with V1 via V2 stack; V1 still independently runnable.
- **Rollback:** disable Profile 0; V1 standalone unaffected.
- **Difficulty:** M. **Impact:** High.

### MP1 — Profile 1: framed OOK + preamble + CRC
- **Goal:** first new PHY — fixed-rate OOK, preamble-based deterministic sync, length + CRC; TX (torch) + RX.
- **Why this order:** biggest reliability jump, least optical risk; deterministic preamble replaces heuristic sync (fixes the V1 lock dilemma structurally).
- **Files/modules:** `lib/v2/phy/profile1_ook/*`, `lib/v2/sync/preamble_sync.*`, `lib/v2/transport/frame_codec.*`, `lib/v2/tx/torch_emitter.*`.
- **Dependencies:** MV4, E1. Reuse V1 torch timing engine concept.
- **Validation:** loopback unit tests (Modulator→Demodulator); two-phone field test; CRC catches corruption.
- **Success criteria (vs M00):** reliable framed message TX↔RX at bare-phone range; deterministic lock; ≈0 idle false locks; ≥95% delivery target progressed.
- **Rollback:** disable Profile 1; Profile 0 + V1 remain.
- **Difficulty:** L. **Impact:** **Critical**.

## Phase 4 — Reliability

### MF1 — FEC (Reed-Solomon) + interleaving + soft-decision
- **Goal:** Profile 2 (Manchester + RS); Extraction emits soft values; recover dropouts without retransmit.
- **Why this order:** needs a working framed link (MP1) to code over.
- **Files/modules:** `lib/v2/link/fec_*`, `lib/v2/phy/profile2_manchester/*` (reuse a proven RS library).
- **Dependencies:** MP1.
- **Validation:** inject erasures/bursts in loopback → recovered; device dropout test.
- **Success criteria:** measurable error-rate / effective-range improvement over MP1.
- **Rollback:** fall back to Profile 1.
- **Difficulty:** L. **Impact:** High.

### MF2 — ARQ/ACK half-duplex session
- **Goal:** two-way turn-taking, ACK + retransmit.
- **Why this order:** needs reliable frames (MF1) + turnaround timing model.
- **Files/modules:** `lib/v2/session/*`.
- **Dependencies:** MF1, E1 (turnaround timing).
- **Validation:** two-phone two-way exchange; forced-loss retransmit test.
- **Success criteria:** reliable bidirectional messaging; graceful one-way fallback.
- **Rollback:** disable session layer; one-way profiles remain.
- **Difficulty:** L. **Impact:** Med-High.

## Phase 5 — Range/robustness increments (each optional, behind interfaces)

### MR1 — Matched-filter detection · MR2 — Temporal integration/stacking · MR3 — Adaptive link (profile negotiation)
- **Goal:** SNR-optimal detection, √N weak-signal integration, condition-adaptive profile stepping.
- **Why this order:** pure range/robustness polish after a reliable link exists; each slots behind unchanged Vision/PHY interfaces.
- **Files/modules:** within `lib/v2/vision/*`, `lib/v2/session/*`.
- **Dependencies:** MV4 / MP1 / MF1 respectively; informed by E3.
- **Validation:** field range tests vs baseline; A/B with feature off.
- **Success criteria:** measured range/reliability gain, no stability regression.
- **Rollback:** feature-flag off → prior behavior.
- **Difficulty:** M–L. **Impact:** Med-High.

## Cross-cutting rules (every milestone)
- Additive only — new `lib/v2/`; V1 `lib/features/` untouched; V1 selectable/runnable after every milestone.
- Runnable state — builds, `flutter test` green, analyze 0 new, incomplete work behind a flag.
- Test-first where logic is pure — synthetic inputs at every layer (frames, SNR, candidates, chips, symbols, FEC blocks, loopback).
- Living docs — M00 metrics + E1–E4 results update the architecture docs before dependent subsystems are built.
- Rollback = revert the milestone commit or disable its flag; never destabilizes V1 or earlier V2 milestones.
- **Review gates:** mandatory STOP after each of E1–E4; final roadmap review before any Phase 0 code.

## Critical path & risk summary
**M00 defines "done"; E1 (timing) and E3 (SNR range) are make-or-break** — they can invalidate PHY-timing and Vision-range designs while changes are cheap. **MV3 (Kalman+IMU) and MP1 (framed OOK + preamble)** are the two highest-impact builds — the real motion fix and the first true V2 link. Everything after MP1 is additive reliability/range polish.
